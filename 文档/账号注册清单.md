开发方给了一份 9 项的清单。**基础设施部分比本文档原版更规范，已采纳**；但缺了数据层与风控层共 9 项必须项，另有两处判断需要修正。

### 采纳开发方的三点改进

| 改进 | 原本 | 采纳后 |
|---|---|---|
| **环境分离** | 只写"云服务器" | **staging / prod 双套**，贯穿 AWS、Firebase、Stream、Privy 所有服务 |

### 两处需要修正

**① Hyperliquid「不用申请账号」——只对一半**

交易本身确实不需要注册（只要有钱包）。但如果要**对订单抽成**（builder fee，这是 perp 侧唯一的收入来源），必须申请 **builder code**。不申请就等于白送流量——调研查到的行业教训是 MetaMask 收满 0.1% builder fee 仍被描述为"悄然亏损"，而 Phantom 靠这个拿了 $12.6M+。

另外 agent wallet 那句「由 Privy 运行时创建」需要补一个约束：**它必须只能交易、不能提现**。这是后端被攻破时的唯一防线，要在 Privy Policy 里显式配置并验证。

**② 缺 D-U-N-S 编号**

清单里有 Apple Developer Organization 和 Google Play Organization，但两者都**以 D-U-N-S 编号为前置**。D-U-N-S 申请周期 5 个工作日到 2 周，不先办这个，那两个组织账号根本开不出来。这是清单里唯一有硬周期、且会阻塞提审的一项。

### Stream vs 腾讯云 IM：一个需要拍板的真实分歧

开发选了 Stream（Chat + Video），本文档调研推荐的是腾讯云 IM + TRTC。两者各有道理：

| | Stream（开发选择） | 腾讯云 IM（调研推荐） |
|---|---|---|
| **Flutter SDK** | ✅ 全场最好（`stream_chat_flutter` v10.3.0，月下载 4.16 万，264 个版本） | ✅ 官方 `tencent_cloud_chat_sdk` 7.x + TUIKit |
| **20 万人单群** | ⚠️ **未经证实**。官方"百万 watcher"指直播弹幕场景；开启 Dynamic Partitioning 后 @提及/已读/reaction 是否降级未知 | ✅ Community 群默认 10 万，企业版工单可扩至 100 万，带历史漫游 |
| **语音房** | ✅ 同厂 Stream Video，$0.30/千参与者分钟（最低价档之一） | ✅ 同厂 TRTC |
| **10 万 DAU 成本** | $4,000~9,000/月（必议价） | $2,300~4,300/月 |
| **中国团队开发** | ⚠️ 未被墙但无国内节点，开发期有延迟 | ✅ 原生无障碍 |

**我的判断：Stream 可以选，但有一个必须先拿到书面答复的问题。**

理由是 20 万人群不是 Day-1 需求——上线时不会有 20 万人的群。Stream 的 Flutter SDK 质量与单厂商省心是实打实的当下收益，而换 IM 供应商的代价主要在**历史消息迁移**，这个代价随时间增长。

所以：**现在就问 Stream 销售一个问题** —— "单个 channel 到 20 万成员时，@提及、已读回执、表情反应、消息搜索分别会不会降级？需要开什么档位？"拿到书面答复再签年费。如果答案是"会降级"，那要么接受群上限降到几万（产品需求改），要么换腾讯云。

成本差约 2 倍（10 万 DAU 时每月多 $1,700~4,700），这个溢价换 Flutter SDK 质量，我认为在团队小、AI 写代码的情况下是值得的——SDK 文档质量直接决定 AI 生成代码的正确率。

这两件事不能等开发完再办。**建议本周内启动。**

### 2. 有一个硬约束：所有法币出入金通道都不支持中国大陆用户与 CNY

调研已确认：Transak、MoonPay、Ramp、Banxa、Mercuryo 全部不支持中国大陆用户和人民币。如果目标用户含中国大陆，出入金这条路走不通，需要另想方案。**这是产品层面的约束，不是技术问题。**

### 3. 注册主体统一用公司，不要用个人邮箱

所有账号都用**公司域名邮箱**注册（如 `dev@公司域名.com`），并开启双因素认证。原因：
- 个人账号后续无法转移，人一走账号就废
- 部分服务（Apple、支付通道、KYC）要求企业实名，个人账号需重新申请
- 建议建一个共享邮箱组，凭证进密码管理器（1Password / Bitwarden 团队版），不要发微信/QQ

这是 Flutter 可行性调研给出的硬性要求：**这三条任何一条不通，架构就要调整。在验证通过之前不要开始写业务 UI。**

| # | 验证项 | 为什么是卡口 |
|---|---|---|
| 1 | **iOS 工程共存** —— `privy_flutter`（要求 Swift Package Manager）+ 语音 SDK + `flutter_inappwebview` 在同一 iOS 工程编译通过并跑通 | Privy 强制走 SPM，而 SPM 与传统 CocoaPods 插件混用在部分插件上仍有兼容问题，CI 脚本也要改。**这是最可能推翻工期估算的隐蔽风险** |
| 2 | **Privy 能否签 Hyperliquid 的非常规域** —— 用 `ethSignTypedDataV4` 签 `chainId: 1337` / `name: "Exchange"` 的 typed data，并在 Hyperliquid testnet 校验通过 | Privy 可能因 chainId 不在已配置链列表而拒签。这是**全部架构建议的前提**，不通则 perp 路线要重做 |
| 3 | **agent wallet 全链路** —— App 内 Privy 签 `approveAgent` → 后端 agent wallet 用官方 Python SDK 在 testnet 成功下单 | 验证"签名下沉后端"这套安全模型真的能跑通 |

**建议把这三条写进合同的第一个里程碑，验证报告作为交付物。** 这比先出 UI 更能降低项目风险。

## 六、必须让项目方知道的三个风险

### 1. 永续合约在 iOS 上有结构性障碍

Apple 审核指南 3.1.5(iv) 要求：加密期货类 App 必须由**持牌银行/证券公司/FCM 提交**。LOOP 主体不是，属结构性不合格。

**旁证**：Hyperliquid 官方 App 在 2026-04 只发了 Android 版，iOS 至今未上——连协议方自己都过不了。

**这意味着**：iOS 版可能无法提供永续合约下单功能。需要项目方拍板：接受（iOS 只做现货）还是寻找持牌实体合作。

### 2. 上架策略建议双轨制

商店上传"合规瘦身版"（行情 + 非托管钱包 + 聊天 + 只读 Launchpad），完整功能走 PWA。

**关键护城河**：Google Play 2026-01-28 生效的新政策中，**非托管钱包明确豁免**。坚持非托管是最大的合规优势，不要动摇。

高风险点：Launchpad（Apple 3.1.5 禁 ICO/类证券发行，Google Play 禁盲盒抽奖与"赚钱"叙事）、App 内 Swap（3.1.5(ii) 是高频拒审点）、挖矿激励（"赚钱"叙事）。

### 3. 钱包供应商锁定会连带锁死社交身份

更换嵌入式钱包供应商必然更换用户地址。而 LOOP 把社交身份建在地址上，换供应商 = 社交图谱断裂，比普通 App 严重得多。

**对策（必须在写第一行身份代码前定下）**：身份系统用**内部 user id 做主键**，钱包地址作为可挂载凭证。这样换供应商时社交关系不丢。

IM 侧有一条同源的硬约束：**IM 的 UserID 必须用与钱包无关的随机内部 ID**。如果直接拿钱包地址当 IM UserID，匿名承诺当场失效——任何人都能从聊天身份反查出地址和全部持仓。

## 附：两条影响页面设计的技术约束

这两条来自 IM 选型调研，会改变 UI 实现方式，写在这里以免开发时踩坑：

**1. Token 卡片消息只存标识字段，价格在渲染时才拉**

聊天消息是永久存储的。如果把价格、涨跌、流动性一起写进消息 payload，三个月后翻历史消息会看到过期价格——用户可能据此做交易决策。

正确做法：消息里只存 `{chain, contract_address, ticker}`，客户端渲染时实时调行情 API 补齐价格与风险分。这也意味着 Token 卡片需要有「加载中」和「数据拉取失败」两个状态（已列入页面清单 E5 的关键状态）。

**2. 大群不做端到端加密**

三家主力 IM 均不支持大群 E2EE，20 万人群做 E2EE 在密码学上也不现实（密钥分发与成员变更的开销随成员数爆炸）。

建议：**E2EE 只在 1:1 私聊考虑**。现原型群聊页顶部写的「end-to-end encrypted」提示需要修正，否则是虚假承诺。
