## 二、修正：Hyperliquid 需要申请 builder code

**交易本身不需要注册账号，这点开发说得对。** 但有两件事要补：

### 2.1 builder code 必须申请（这是 perp 侧唯一收入来源）

不申请 builder code，第三方前端**无法对订单抽成**，等于白送流量。

行业教训（调研数据）：
- Hyperliquid builder 累计分成 $64M，但极度集中于 Phantom（$12.6M+）
- MetaMask 收满 0.1% builder fee 仍被描述为"悄然亏损"

**建议**：立刻申请，并在合同里明确抽成费率归属方。

### 2.2 agent wallet 的权限边界必须显式约束

开发说「用户 Master Wallet 和 Agent Wallet 由 Privy 运行时创建」——架构对，但要补一条硬约束：

> **Agent Wallet 必须配置为「只能交易、不能提现」。**

理由：agent wallet 私钥在后端。这条约束是后端被攻破时的唯一防线——最坏情况变成"乱下单"而不是"资产被卷走"。

**验收要求**：在 Privy Policy 里显式配置，并在第 1 周的 Go/No-Go 3 里实测验证（尝试用 agent wallet 发起提现，必须失败）。

### 2.3 补充：测试钱包要准备两套

公司测试钱包除了 Hyperliquid testnet，还需要各 EVM 链 + Solana 的 testnet 资金（现货 Swap、跨链、授权拦截都要在 testnet 验证）。

## 三、Stream vs 腾讯云 IM：需要拍板

开发选 Stream，调研推荐腾讯云。**两者都可行，但有一个必须先问清的问题。**

### 3.1 立刻问 Stream 销售的问题

> "单个 channel 成员数达到 20 万时，@提及、已读回执、表情反应、消息搜索分别是否降级？需要什么档位？Dynamic Partitioning 开启后有哪些功能限制？"

**为什么必须问**：Stream 官方材料里的"百万 watcher"指的是**直播弹幕场景**（只读观众），不是带完整消息语义的社区群。产品需求是 20 万人社区群且要 @提及和表情反应，这两者可能冲突。

**拿到书面答复再签年费。**

### 3.2 两家对比（供决策）

| | Stream | 腾讯云 IM + TRTC |
|---|---|---|
| Flutter SDK 质量 | ✅ **全场最好**（月下载 4.16 万，264 个版本，`attachmentBuilders` 自定义渲染是一等公民） | ✅ 官方 SDK + TUIKit 现成 UI |
| 20 万人单群 | ⚠️ 未经证实 | ✅ 默认 10 万，工单可扩 100 万，带历史漫游 |
| 自定义 Token 卡片消息 | ✅ 支持 | ✅ customElem 任意 JSON |
| 自定义匿名身份 | ✅ JWT | ✅ UserSig 自签发 |
| 语音房 | ✅ Stream Video，$0.30/千参与者分钟 | ✅ TRTC |
| 1 万 DAU | $2,000~2,800/月 | $1,000~2,600/月 |
| 10 万 DAU | $4,000~9,000/月（议价） | $2,300~4,300/月 |
| 中国团队开发体验 | ⚠️ 无国内节点，有延迟 | ✅ 无障碍 |

### 3.3 我的建议：可以选 Stream

理由：

1. **20 万人群不是 Day-1 需求**，上线时不会有这个量级
2. **SDK 文档质量直接影响 AI 生成代码的正确率** —— 在"AI 写代码 + 人工审核"的模式下，这是实打实的收益，不是虚的
3. 单厂商（Chat + Video 一家）少一套鉴权和状态同步的胶水代码
4. 成本溢价约 2 倍，但绝对值在 10 万 DAU 时是每月多 $1,700~4,700，可接受

**风险与对策**：换 IM 供应商的主要代价是历史消息迁移，且随时间增长。所以 3.1 的问题必须**现在**问，不要等到有了 10 万条历史消息再发现群上限不够。

### 3.4 如果选 Stream，注意一个 API 稳定性问题

Stream 的自定义消息渲染 API 在 v7→v10 之间改过两次（`customAttachmentBuilders` 废弃 → `attachmentBuilders` → v10 的 `StreamComponentFactory`）。

Token 卡片消息是产品核心功能，**要向 Stream 确认 v10 的 API 是否稳定**，否则每次大版本升级都要重写这一层。

## 四、Privy：四项必须拿到书面答复

开发选 Privy 正确——调研确认它有**官方 Flutter SDK**（`privy_flutter` v0.10.1，支持 EIP-712 + Solana），是唯一同时覆盖「嵌入式钱包 + 策略引擎 + Agent 签名 + 官方 Hyperliquid recipe」四件事的供应商。

但有四件事要书面确认：

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | **私钥导出功能是否可能被单方面关闭？** | 这是唯一的逃生舱，也是抗辩"非托管"的技术依据。要写进合同 |
| 2 | **Flutter SDK 何时脱离 beta？** | 现为 v0.10.1（0.x），且 **GitHub 仓库 404 不可访问** —— 出 bug 无法自救，只能等官方修 |
| 3 | **是否服务中国大陆用户？** | 调研完全查不到，必须直接问 |
| 4 | **Enterprise 报价** | **1 万 MAU 即触发议价区间**，现在就要谈，不要等到超量 |
| 5 | **内置 Swap 能否设置 affiliate fee？** | 已决定 Swap 走 Privy 内置。**如果不能抽成，现货侧就没有交易收入**，只剩 perp 的 builder fee（0.1%）。这直接影响商业模型 |
| 6 | **内置 Swap / 跨链的 Flutter SDK 支持度** | 官方文档的 swap 示例多为 Web/RN，需确认 `privy_flutter` 是否同样暴露这些方法 |

> 注意：Privy 已被 Stripe 收购（2025-06）。不会倒闭，但定价与产品优先级服从母公司，**建议在合同里锁定价格有效期**。

**Plan B**：`web3auth_flutter` v7.0.0（版本号比 Privy 成熟）。Dynamic / Magic / thirdweb / Para 在 Flutter 上都不可用，不要考虑。

## 八、开工第一周的三个 Go/No-Go 验证

**这三条任何一条不通，架构就要调整。验证通过前不要开始写业务 UI。** 建议写进合同第一个里程碑，验证报告作为交付物。

| # | 验证项 | 为什么是卡口 |
|---|---|---|
| 1 | **iOS 工程共存** —— `privy_flutter`（要求 SPM）+ 语音 SDK + `flutter_inappwebview` 同工程编译并跑通 | Privy 强制走 Swift Package Manager，与传统 CocoaPods 插件混用有已知兼容问题，CI 脚本也要改。**这是最可能推翻工期估算的隐蔽风险** |
| 2 | **Privy 能否签 chainId 1337** —— 用 `ethSignTypedDataV4` 签 Hyperliquid 的非常规域并在 testnet 校验 | Privy 可能因 chainId 不在已配置链列表而拒签。这是 perp 架构的前提，不通则要改用独立 EOA 方案（+8~12 人日） |
| 3 | **agent wallet 全链路** —— App 内签 `approveAgent` → 后端 agent wallet 用官方 Python SDK 在 testnet 下单成功；**且尝试提现必须失败** | 验证"签名下沉后端"的安全模型真的成立 |
