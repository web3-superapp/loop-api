## 一、这个计划成立的条件与不成立的地方

先说结论，避免看完 6 周排期才发现前提有问题。

### 30 天能装下的量

审核是唯一不可压缩的串行资源。每天 3.5 小时 × 30 天 = **105 小时审核预算**。这决定了整个计划的吞吐上限，不是 AI 的生成速度。

按代码类型分配这 105 小时：

| 代码类型 | 预估行数 | 审核方式 | 小时/千行 | 小计 |
|---|---:|---|---:|---:|
| UI 层（47 屏布局与样式） | ~17,500 | 看截图 + 扫代码结构 | 1.2 | 21 h |
| 业务逻辑 / 状态管理 / 列表分页 | ~7,500 | 读关键路径 + 看测试结果 | 2.5 | 19 h |
| **资金相关**（签名、精度、强平价、授权、agent wallet） | ~6,500 | **逐行读 + 自己算一遍 + testnet 实测** | **6.0** | **39 h** |
| 后端 API / 数据聚合 | ~3,000 | 读接口契约 + 看集成测试 | 2.0 | 6 h |
| 配置 / CI / 脚手架 | ~2,000 | 抽查 | 0.8 | 2 h |
| **合计** | **~35,500** | | | **85 h** |

**85 小时 < 105 小时预算，剩 20 小时缓冲（19%）。**

三次决策对缓冲的累计影响：

| 决策 | 变化 | 缓冲 |
|---|---|---|
| 初版（A 档 48 屏，全自建聚合器） | — | 11% |
| 决策 7、8（perp 只做核心市场 + 去 AI 包装，删 2 屏） | −3 h | 14% |
| **决策 9（Swap/跨链走 Privy 内置）** | **−5 h**（少约 1,500 行聚合器封装与路由 UI） | **19%** |

**资金相关的 39 小时始终没减。** 这是刻意的——三次削减都只动了"能买到就不自己写"的部分，签名、精度、强平价、授权拦截这些必须逐行审的代码一行没省。19% 的缓冲现在能吃下一次 Go/No-Go 失败的返工。

缓冲会被三件事吃掉：返工、Go/No-Go 验证失败后的架构调整、iOS 音频会话与 SPM 兼容这类"不可预估的坑"。

### 明确不成立的三件事

| # | 事项 | 为什么 |
|---|---|---|
| 1 | **不含安全审计** | 钱包类产品的第三方安全审计周期是 2~4 周且独立报价，不可能塞进这 30 天。内测版不涉真实资金可以延后，**但正式上线前必须做** |
| 2 | **不含上架审核** | Apple 重审金融类 App 常需 1~3 周，且可能反复。这次交内测版正好绕开，但要知道这是**推迟不是消除** |
| 3 | **iOS 上没有 perp 下单** | Apple 3.1.5(iv) 要求加密期货 App 由持牌机构提交。内测阶段 TestFlight 可以放，**但正式上架时 iOS 必须去掉 perp**。这不是工期问题，是结构性限制 |

### 一个必须接受的风险

**第 1 周的三个 Go/No-Go 验证如果失败，30 天不成立。**

其中最危险的是「Privy 能否签 Hyperliquid 的 chainId 1337 域」——它是整个 perp 架构的前提。如果 Privy 拒签，方案要改成"用户在 App 内额外生成一个独立 EOA 专用于 Hyperliquid"，这会新增约 8~12 人日，且要重新设计密钥保管方式。

**因此第 1 周排的是验证不是开发。这一周不产出业务 UI 是刻意的。**

## 二、审核纪律（这是计划能跑的关键，不是形式）

AI 写代码的失败模式和人不一样。人是"没想到"，AI 是"看起来对但细节错"。所以审核重点要相应调整。

### 分级审核规则

| 级别 | 适用范围 | 审核动作 | 不允许省略的 |
|---|---|---|---|
| **R0 逐行审** | 签名构造、私钥处理、agent wallet 授权、金额精度换算、强平价与保证金计算、授权额度改写 | 逐行读 + **自己独立算一遍数值** + testnet 实测 + 边界值手测 | 数值必须自己复算，不能只看 AI 说"已验证" |
| **R1 关键路径审** | 交易流程编排、状态机、错误处理、路由、缓存失效 | 读主路径与错误分支 + 跑自动化测试 | 错误分支必须读，AI 最爱漏这里 |
| **R2 截图审** | 47 屏 UI 布局、样式、动效、空/加载/错误态 | 看截图对比设计稿 + 扫代码找硬编码 | 移动端适配必须真机看，模拟器会骗人 |
| **R3 抽查** | 配置、CI、工具脚本、国际化文案 | 抽 20% | — |

### 每天的固定节奏（3.5 小时怎么花）

```
0:00–0:30   看昨天夜里 AI 的产出清单 + 自动化测试报告，决定今天审什么
0:30–2:00   R0/R1 深度审（每天必须留够 1.5 小时给资金相关代码）
2:00–3:00   R2 截图审 + 真机点一遍当天新增页面
3:00–3:30   写审核意见、标记返工项、给 AI 下一批任务
```

**硬规则：R0 类代码未通过审核，依赖它的下游任务不许开工。** 宁可让 AI 空转去做 UI，也不要在未验证的签名逻辑上叠功能——那样返工是成倍的。

### 三条必须自动化的检查（省人工审核时间）

这三样投入约 3 人日建设，能省下十几小时人工审核，值得在第 1 周做：

1. **金额精度属性测试** —— 随机生成大量金额做 wei/decimal 往返转换，断言无精度丢失。这类 bug 人眼极难看出
2. **47 屏截图回归** —— 每次构建自动截 47 屏，与基线比对，只把变化的屏推给人看。**这是 21 小时 UI 审核能压下来的主要原因**
3. **签名向量测试** —— 把 Hyperliquid 官方 Python SDK 的签名结果作为标准答案固化成测试向量，后端每次改动自动比对

## 三、六周排期

每周格式：AI 开发任务 → 人工 Review 卡口 → 本周出口标准（不达成则不进下一周）。

### 第 1 周 · 验证与地基（不产出业务 UI）

**这一周的价值是把最可能推翻计划的风险前置。**

| AI 任务 | 产出 |
|---|---|
| Flutter 工程脚手架：路由（三级）、状态管理、设计系统（颜色/字号/间距/组件）、暗色主题 | 可跑空壳 App |
| **Go/No-Go 1**：`privy_flutter`(SPM) + 语音 SDK + `flutter_inappwebview` 同工程 iOS 编译跑通 | 验证报告 + 可运行 ipa |
| **Go/No-Go 2**：Privy `ethSignTypedDataV4` 签 chainId 1337 / name "Exchange"，Hyperliquid testnet 校验通过 | 验证报告 + 签名样本 |
| **Go/No-Go 3**：App 内 Privy 签 `approveAgent` → 后端 agent wallet 用官方 Python SDK 在 testnet 下单成功 | 端到端 testnet 成交截图 |
| 后端骨架：BFF 框架、鉴权、Hyperliquid 网关雏形、错误规范 | 可调通的接口 |
| 三条自动化检查建设（精度属性测试 / 截图回归 / 签名向量） | CI 跑通 |

**Review 卡口（R0 级，本周审核重心）**
- 三个 Go/No-Go 的验证过程要**自己复现一遍**，不接受"AI 说通了"
- agent wallet 权限边界：**必须确认它只能交易不能提现**，这是后端被攻破时的唯一防线
- 密钥流向审计：画一张图确认私钥材料不经过后端、不进 WebView、不落日志

**出口标准（硬卡口）**
- ✅ 三个 Go/No-Go 全部通过，且负责人本人复现过
- ✅ CI 能自动跑三类检查
- ❌ 任何一个 Go/No-Go 失败 → **停下重新评估架构与工期，不要带着未验证的假设进第 2 周**

**Review 卡口**
- **R0 逐行**：金额精度换算（各链 decimals 不同，USDC 6 位 vs ETH 18 位是经典事故点）。**必须自己算几个边界值**
- **R0 逐行**：F4 地址风险校验与 F5 gas 估算。首次转账提醒、高风险地址拦截不能只是 UI 摆设
- **R0**：Bridge 进度追踪的**失败与需手动 claim 分支**——跨链卡住是真实高频场景，用户会以为钱丢了
- **R1**：Swap 报价过期刷新逻辑、滑点保护

- **R2**：K 线在真机上的手势（缩放/拖拽/切周期）不能和页面滚动冲突

**出口标准**
- ✅ 闭环跑通：Market 发现 → Token 详情看风险 → Swap 买入 → Wallet 看到持仓
- ✅ 精度属性测试全绿
- ✅ 跨链在 testnet 完成一次，且中途杀 App 重开能看到正确进度

- **R0**：F17 批量回收授权的交易构造
- **R1**：DApp Browser 的签名请求**全部走 App 内 Privy 弹窗**，WebView 拿不到任何私钥材料
- **R1**：I5 地区限制的开关逻辑（与出入金、perp 联动）
- **R2**：47 屏全量截图回归对齐；真机跑完整闭环三遍

**出口标准**
- ✅ 47 屏全部可达，无死路
- ✅ DApp Browser 能拦下一次真实的无限授权请求并给出限额建议
- ✅ TestFlight 与 APK 装机可用，Sentry 有数据
- ✅ 断网/弱网/杀进程重启三种异常下不崩、不丢状态

## 四、风险与缓冲消耗预案

19% 的缓冲（约 20 小时）比初版宽裕，但仍可能被吃掉——尤其是第 1 周 Go/No-Go 失败或第 4 周音频会话超预期。按优先级给出削减顺序——**真到了要削的时候，按这个顺序削，不要临时拍脑袋**：

| 顺序 | 削减项 | 影响 | 为什么可以先削 |
|---:|---|---|---|
| 1 | B4 全局搜索、E12 消息搜索 | 少两个入口 | 不在闭环上，用户可用列表页替代 |
| 2 | C3 全屏 K 线（保留内嵌图表） | 看图体验降级 | 内嵌图表已够看趋势 |
| 3 | D7/D10/D11（成交历史/出入金/资金费率详情） | perp 功能不完整 | 不阻塞下单闭环 |
| 4 | E10 语音房完整视图 | 只有内嵌卡片形态 | 内嵌卡片是已拍板的主形态 |
| 5 | H 组只留 H1 Profile | 设置项变少 | 内测版可接受 |
| **不许削** | **F11 签名弹层、F16 授权拦截、D3 下单确认、A6~A10 私钥五屏、I 组系统页** | — | 削这些等于交一个会让用户亏钱的内测版 |
