# LOOP 管理与人工运营工作台方案

状态：用户于 2026-10-03 确认；进入实施，功能完成度见交接验收记录。

## 目标与代码基准

用户要求同时开发 App 社区/群聊管理与平台运营后台，并从现有代码找全需要人工运营的配置，特别是挖矿系数。延续非合约先做、合约只更新交接的边界。

移动端：`web3-superapp/loop-mobile`，`724b34f`；已有 PR #5 保留独立审核。本轮建议新增管理分支，以该提交为基础，不把新范围直接混入原 PR。
后端：`web3-superapp/loop-api`，多人开发分支 `integration/v2`，固定基准 `83f5ac7a9de654d28a0628f38a79db44a0c6221b`。GitHub 当前组织只有 mobile/API 两个仓库，未发现独立后台仓库；本地后端此次为只读审查副本。

## 方案取舍

1. **建议：App 管理页 + 独立 Web 运营工作台 + API 管理边界。** App 服务社区所有者/管理员；Web 服务平台运营、审核、客服、审计。复用已有服务而非在浏览器执行脚本，数据和权限统一由 API 控制。一次补齐身份、审批、版本和审计基础，以后新配置按同一方式扩展。
2. 全部放在 Flutter App：入口少，但平台批量审核、表格导入、版本差异查看不适合手机，并增加高权限误入风险，不建议。
3. 仅给现有脚本加表单：最快，但身份、审计、并发和不明结果恢复不完整，不作为交付方案。

## App 管理结构

沿用已有卡片和绿/白/黑风格，不新增一级 Tab。社区资料页对有治理权限的用户提供「管理」入口；成员、管理员、禁言/封禁、社区资料、语音主持集中展示。成员搜索保留后端前缀搜索；列表遵循移动端滚动追加；对成员的动作只取后端 `items[].actions`，不能仅看当前用户是 admin 就放行所有操作。

现有社区管理可复用 `CommunityGateway.changeMemberRole/setMuted/setBanned/editProfile`；所有权转让、封禁等先确认后请求，失败不改变本地结果，权限变更后重读资源。封禁不等于移除：现有 unban 恢复活跃成员并重新加入官方频道，页面按实际语义表达。

普通私群与社区是不同模型。当前 `GroupInfoScreen` 的成员管理/资料/通知均明确 deferred，只有退出已闭合。补普通群资料、成员目录、邀请、移除、角色和所有权转让时必须新增相应后端模型与 provider 对账；不能套社区 ID 或客户端调用 Stream 管理权限绕过后端。普通成员只能管理自己的通知/退出；其他操作来自服务端逐目标权限。

## 平台后台信息架构

一级菜单：待办、社区与用户、项目与资产、挖矿配置、推荐与内容、客服、操作记录。权限管理只对授权管理员展示；技术运维作为独立受限区域。

桌面采用固定侧栏、紧凑数据表格、详情侧板；筛选和状态在列表顶部，修改在侧板完成，涉及范围/资金意义的配置有独立差异确认。关键数字和状态优先，避免装饰性仪表盘。适配小屏但不把平台全量批处理塞进 App。延续产品黑白绿配色和系统字体，表格正文 14–16、辅助 12–13、标题 20–24。不同状态用文字和图标，不只靠颜色。

## 挖矿配置特别说明

现有 dev-baseline 的 assetWeights 默认 `1`、community range `0.5`–`2`；每日产出是明确 development_placeholder。产品交接是社区 `0.1`–`1.0`，LOOP 基础 `1.0`。两个版本分开展示，不能将开发占位值作为产品默认或就地覆写历史。

现有引擎的社区权重是资产权重之外的第二个因子，不是同一个参数的别名。表单展示资产权重、社区系数以及组合结果；必须与现有 snapshot 计算方法核对，不在 UI 重新实现另一套公式。

数据类型：金额、权重、预算和百分比沿用 decimal string；guardBps 使用后端现有整数边界（1–10000）。资产键只用 canonical assetId；社区必须绑定资产；同一公式版本对同一资产的社区权重冲突必须拒绝。参考价失败/过期不能填写常数强行结算。

**必须先修复版本存储。** 当前 `mining-repository.ts::setCommunityWeight` 使用 `on conflict (community_id) do update`，一社区仅保留一行；给待审批公式录入权重会覆盖旧公式的权重。不能在这个存储模型上直接开放配置界面。迁移后草稿单独存储，已发布社区权重至少以 `(configVersion, communityId)` 唯一定位且不可改写；历史存量只迁移有证据的版本关系，无法恢复的历史输入明确标记不可复算，不补造。

拟采用草稿编辑→校验/试算→提交审批→独立审核人「批准并立即发布」→生成快照的流程。首版只有一个批准并发布操作，事务内同时退休旧版本、激活完整新版本；不拆成含义模糊的批准/发布按钮，不提供定时发布。待审包包含公式、全部社区权重、价格规则及其规范化 contentHash；编辑后原审批失效，重新提交。发布必须检查 `expectedActiveVersion` 与 `draftRevision/contentHash`，绑定批准的完整内容并原子切换，不能出现新公式配旧系数的中间状态。

发布页显示新旧差异、影响资产/社区、当前版本、适用环境和生效规则。试算调用同一算力引擎，保存输入区块/快照、价格版本与完整输入 hash；复算不得重新拉取实时价格冒充原输入，不发布余额或奖励。当前 approveFormula 仅校验 requestId 格式，尚不等于具备持久化幂等结果；新管理接口必须补齐下节规定。

产品双矿池/NFT 权重、实际可领取奖励、税率、资金买入/转出、链上 root 与预算拨款仍属于合约交接。后台可维护审核草稿和执行证据，但不发送链上交易、不把显示值当奖励承诺。保留现有 production 禁用边界，开发管理控制台的完成不等于放开生产经济模型。

## 权限、持久化与写入规范

独立 `/ops` Web 入口和管理 API 命名空间；普通移动端 Token 不因进入 URL 而获得平台权限。复用已有身份校验后由服务器查操作员授权。平台角色建议：只读审计、客服、社区/内容运营、项目审核、挖矿配置编辑、配置审批、系统管理员。初始授权只能由部署管理员受控注入；不提供公开注册成管理员或自我提权。

App 社区权限继续使用现有 owner/admin/member 逐目标矩阵。平台操作员不要求加入每个社区，也不能冒充 owner 调用已有方法；使用独立平台授权和显式范围：社区审核只允许授权范围内的审核动作，客服只能处理授权工单，配置编辑/审批只允许对应资源。跨社区操作必须有明确的全局授权或社区集合范围，并逐对象检查。平台强制所有权转让、处置社区 owner、全局账号封禁等尚无确认契约，首版禁用；不得从普通社区 admin 权限推导。普通群创建者/管理员权限另立契约，不自动继承平台角色。

配置和审批使用数据库持久化，明确 draft/review/published 状态、版本 CAS、操作者、理由、审批者和变更摘要。高影响参数编辑者不能审批自己提交的版本；关键权限管理单独审计。操作员身份由服务器记录，不能由表单填 reviewer 字符串冒充。

每次写入使用稳定 operationId，服务端持久化绑定操作者、动作、目标及规范化请求 hash；同 ID 不同内容拒绝，同 ID 同内容重试返回已记录结果。业务状态、版本 CAS、审批者身份、审计及幂等结果在同一数据库事务内提交。操作记录可查询，网络断开/未知结果先对账，不能重新生成 ID 重复执行。原业务事件和通知可复用；不得把脚本内每次 randomUUID 的行为直接复制成 HTTP 自动重试。审计与状态改变的事务边界逐命令定义；数据库成功、供应商待同步、通知失败是不同状态。provider/通知采用可恢复且去重的任务并独立记录结果；任务执行前重新检查有效授权和已批准版本，权限撤销后的排队管理动作不得继续执行，记录为需重新授权/审核。不能把已完成的业务事务因为通知失败重新执行一遍。

Web 不接数据库、不能持有 provider secret、不能提交任意命令执行。密钥、RPC 凭据、主网/支付开关不进入普通运营表单，继续由部署配置管理；后台只显示脱敏状态。认证和管理权限跨边界需要编号决策、正式 schema、负向权限测试和生产启用检查。服务缺少依赖时明确不可用，离线演示和生产连接分离。

## 分批实施与完成口径

A. 建立后台身份/权限/审计/任务/版本基础；先打通现有社区审核、挖矿公式/权重/审批/快照和客服真实服务。每一项必须可读取、保存、查询结果，并能在原 App/API 消费端看到效果。
B. App 管理入口集中化与普通群管理补齐；平台项目审核、资产池登记、白名单计算、销售登记、里程碑接入。
C. 新增推荐/活动/公告配置与 App 消费；邀请加成规则、平台用户/内容治理、AI 文档管理按各自契约和权限逐项交付。不能以表单存库代替规则生效或 provider 执行。
D. 技术运维任务单独受控接入；合约相关只交接。每批记录可用模块与未验收项，不能将未接通模块显示为可执行。

不把管理后台的安全基础拆成假登录 UI；先让一组完整业务贯通，再扩大菜单。本文件涵盖全范围，分批顺序不代表其余项取消。

## 验收

- 普通用户访问管理 API 被拒；跨社区/跨角色/自我审批/越权写入被拒；撤销权限后旧会话无管理权限。
- 参数非法/并发编辑/重复提交/超时恢复/发布失败保留旧生效版本；新版本读数与新快照一致。
- 准备下一版权重时，旧版公式与旧版新生成快照仍读取原权重；发布后两版的输入均可定位复算。审批后编辑内容必须使审批失效；并发批准只有一个成功。
- 同 operationId 不同请求被拒；超时重试只执行一次；撤销权限后的排队任务不执行。普通社区 admin、受限平台运营均不能跨范围处置，也不能对 owner 执行未授权操作或给自己提权。
- 社区审核、角色变更、禁言封禁及解封的实际状态与 Stream 同步可追踪；无权限动作不显示为可用。
- 所有可编辑字段必须有对应消费逻辑；运营改动在 App/查询端产生可验证效果，撤回不修改历史事实。
- CSV 原子校验、重复/错误链/地址大小写、允许数量限制；真实资产元数据不可人工覆盖。
- 公式与业务测试、管理路由负向测试、数据库迁移与隔离测试库验收、UI 浏览器检查；原生/供应商/生产未测单列。

## 需要确认的设计选择

是否采用方案 1（独立 Web 运营后台 + App 社区/群聊管理），按 A→D 分批落实，挖矿系数优先贯通、合约和资金执行仍仅交接？此确认不授权任何生产配置变更或真实资金操作。
