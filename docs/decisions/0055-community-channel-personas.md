# Decision 0055: Community channel personas (one name per official group)

- Status: Accepted (main-agent ruling, 2026-09-20; user wording: "每个聊天室一个名字才能达到匿名的效果")
- Date: 2026-09-20
- Scope: `communication` module, `community-channel-sync` worker lane, `GET /v2/communities/{id}` chat projection, one dev operator script. Direct messages (`direct` channels) and Decision 0025 small groups are unchanged.

## Context (F5 evidence, `docs/acceptance/2026-09-19-device-feedback-repro.md`)

- Official community channels are populated by the `community-channel-sync` lane, which calls `addMembers({ user_id })` with no member custom data, and the joining Stream user is upserted `{ id }`-only ("LOOP publishes no profile facts to Stream", `channel-gateway.ts`).
- Stream therefore holds no name for the user, and the Flutter SDK's `User.name` falls back to `user.id`. Every other member in every official group sees the literal Stream user ID `loop_<internal uuid without hyphens>`: the same string in all 21 groups, derived from `loop_users.id`.
- That string is a stable cross-community correlation key and an internal primary key exposed on a public surface, which violates the opaque-ID rule in `00-主代理规则.md` §4.5 and makes the "anonymous group" claim false.
- The Decision 0024 `loop_group_alias` projection exists but is wired only to `POST /v2/chat/groups` (`communication_groups`); both `communication_groups` and `group_alias_reservations` hold zero rows on Development. Official groups never executed that code.

## Decision

### Entity

- One **community persona** per `(community_id, internal_user_id)`. It is generated by the server the first time the member's `add` sync job runs, is immutable, is unique within the community, and never encodes any identifier: shape `<Word>-<4 digits>`, where `Word` comes from a compiled list of neutral English words (251 entries, no brand, no product, no alias fragment) and the digits are uniformly random. Collisions inside a community are retried under the unique constraint; the generator never sees state.
- Stable ID: `personaId` (random UUIDv4, opaque). It is projected to Stream as `loop_group_alias_id`; the alias as `loop_group_alias`; `loop_group_alias_version: 1`. This is byte-for-byte the shape `group-member-gateway.ts` already writes for Decision 0024 groups, so one client renderer covers both.
- Renaming is out of scope for this decision. Decision 0024's `PUT .../me/alias` semantics remain the intended future path; the persona table is designed so a later user-chosen alias would still be unique per community and still immutable once chosen.

### Storage

- New table `public.community_channel_personas` (migration `000031_v2_community_channel_personas`). Reusing `group_alias_reservations` was rejected: its `group_id` is a `not null` FK to `communication_groups`, both unique constraints and the immutability trigger are keyed on it, and the search-key machinery (`alias_search_key`, prefix index) is not needed here. Adding a nullable scope column would weaken the Decision 0024 constraints for no gain.
- Columns: `persona_id` PK, `community_id` FK `communities`, `owner_user_id` FK `loop_users`, `alias`, `alias_version = 1`, `projection_state in ('pending','confirmed')`, `confirmed_at`, `projection_attempts`, `next_projection_at`, `projection_lease` (migration 000032), timestamps. Unique `(community_id, owner_user_id)` and unique `(community_id, alias)`. A row trigger forbids delete and any change to `persona_id`, `community_id`, `owner_user_id`, `alias`, `alias_version`, `created_at`; an insert must start `pending`. A statement trigger (000032) refuses `truncate` — direct or cascaded from `loop_users`/`communities` — while any persona row exists, unless the session sets `loop.allow_persona_truncate = 'on'`; an empty table may still be truncated so schema-reset test fixtures keep working.
- Both FKs are `on delete restrict`: a `loop_users` or `communities` row that owns a persona cannot be deleted while the persona exists. This is deliberate (personas are permanent) and means an account- or community-deletion workflow must be a separate decision that also settles persona retention; the migration `down` refuses to drop the table while rows exist for the same reason.
- LOOP PostgreSQL is the persona authority. Stream member custom data is a projection. `projection_state` is `confirmed` only after a Stream response echoed the exact three fields; every other outcome leaves or returns it to `pending`, and a pending projection is retried with bounded backoff (5 s doubling to 1 h) by the worker's persona lane. A persona is never deleted, recycled, or reassigned, including after leave, ban, or rejoin: the same account resumes the same name.
- **Projection lease (review M2).** Every bookkeeping write is fenced. `ensurePersona` (the add path) and `claimPendingProjections` (the persona lane and the backfill) each issue a fresh `projection_lease` and push `next_projection_at` out (60 s), and `confirm`/`reset` write only `where projection_state = 'pending' and projection_lease = <token>`, clearing the lease. A stale holder therefore never overwrites a newer outcome; a lost lease is logged (`Community persona projection lease was lost; outcome not recorded`) and counted as deferred. `resetProjectionForMember` (the `remove` path) is the one unfenced write: the membership authority knows Stream dropped the member custom, so it forces `pending` and clears any lease.

### Projection paths

1. **New member (`add` job).** The worker calls `ensurePersona` (DB) before the single provider call, then `addMembers` with `add_members: [{ user_id, custom: {loop_group_alias_id, loop_group_alias, loop_group_alias_version: 1} }]`. The gateway reads the `members[]` echo of the update response: if the member entry carries the exact custom, the persona is confirmed under the ensure lease; otherwise it is scheduled for the persona lane with the 5 s-based backoff (never "due now", review L1). The job's own exactly-once-per-lease rule is unchanged (one membership write per lease). If `ensurePersona` itself fails (`CommunicationRepositoryUnavailableError`, i.e. the persona table, not Stream), the job is retried under the job error code `community_persona_unavailable` before the provider is touched; that retry is not counted toward `stream_channel_sync_exhausted` and never marks the channel `failed` (review M1). Persona bookkeeping after `completeJob` is never allowed to turn a completed job into a retry, but a failure there is logged (`Community persona bookkeeping failed after a completed sync job`), never swallowed.
2. **Existing member / re-projection.** `projectMemberPersona` uses Stream `updateMemberPartial` (`PATCH .../member/{user_id}` with `set`), the same call Decision 0024 uses, and validates the `channel_member` echo. The worker's persona lane claims up to 20 pending personas per tick whose LOOP member state is `synced` and whose channel is provisioned and not `failed`, projects each once, and confirms or backs off. A member that is not `synced` is not projected (its persona waits for the next `add`).
3. **Removal.** When a `remove` job completes, the member's persona is reset to `pending` (Stream drops member custom together with the membership). Re-adding goes through path 1.
4. **Backfill.** `pnpm community:persona-backfill --confirm [--max N]` (`scripts/community-persona-backfill.ts`) runs two phases through `CommunityPersonaService`: (a) `synced` members on a provisioned channel that have no persona row get `ensurePersona` (which issues the lease) plus one `projectPersona` under it; (b) pending personas are taken through the same fenced `claimPendingProjections` the worker's persona lane uses. Batches of 50 are paced 200 ms apart; `--max N` bounds the members processed in one run (exit 1 with "More members remain" when it stops early). It is idempotent (confirmed personas are neither claimed nor touched; pending ones are re-projected), refuses `NODE_ENV=production`, requires `DATABASE_URL`, `STREAM_API_KEY`, `STREAM_API_SECRET`, and never restarts a process. **The worker may stay running during the backfill**: phase (b) and the lane claim through the same `for update skip locked` + lease, so a persona is projected by exactly one of them; a persona the lane took meanwhile simply does not appear in the script's counts.

### Contract impact (additive only)

- `GET /v2/communities/{communityId}` `chat` gains `viewerPersona: { alias, projectionState } | null` in all three states. It is the caller's own persona for that community (null before the first `add` job or for a non-member). No existing field changes.
- No read surface returns other members' Stream user IDs; therefore no other response gains a persona field. Member directories keep `publicProfileId`/`loopId`/`alias`, which are the community-scoped public identity, not the chat identity.
- Client rendering rule (written into `docs/frontend-v2-communication-api.md`): in an official community channel, a message author or member row is drawn from `member.custom.loop_group_alias` only; when absent, draw the neutral label "成员"; never draw `user.name` or `user.id`.

### Failure semantics

- Missing Stream credentials: the worker lane is not constructed (existing rule), the persona lane does not run, and the backfill script refuses to start. No fixture, no fake success.
- Provider `unavailable` (5xx, timeout, 429): persona stays `pending`, retried with backoff. Deterministic `4xx` (member not in channel yet, malformed): same backoff; there is no terminal persona state because membership may still catch up and the persona is permanent. Each unconfirmed projection is logged with `personaId`, `projectionAttempts`, and the error class only.
- Persona table unavailable during an `add`: job retried under `community_persona_unavailable` (see path 1); the Stream attempt budget and the channel state are untouched.
- A response that echoes different custom values is treated as unconfirmed, never as confirmed.

## Rollback

- Runtime rollback leaves the table and rows in place; the earlier worker ignores them and stops sending custom on `add_members` (members would again show the Stream ID). Migration 000031's `down` refuses to drop the table while any row exists, consistent with the other communication migrations; 000032's `down` drops only its trigger and the lease column.
- Stream-side custom data is not removed by a rollback; it is presentation data only and carries no identifier.

## Evidence gates

- Unit: generator (list size, uniqueness, forbidden fragments, shape), worker `add`/`remove`/persona-lane paths incl. `community_persona_unavailable` and logged bookkeeping, gateway custom echo validation and `projectMemberPersona`, service incl. lease loss and 5 s-based `requestProjection`, backfill script incl. `--max`, pacing, and the shared claim.
- Integration (PostgreSQL): persona uniqueness and collision retry, idempotent `ensurePersona` with re-lease, fenced confirm/reset (wrong lease, consumed lease, confirmed row), claim filter (due + synced + provisioned only) issuing a lease per claim, immutability trigger, truncate guard with opt-in, `listMembersWithoutPersona` paging.
- Device/provider: unverified until a real Development channel shows `member.custom.loop_group_alias` on both a freshly added member (path 1) and a backfilled member (path 4), and the Flutter renderer draws it. Recorded as unverified in the handover.
