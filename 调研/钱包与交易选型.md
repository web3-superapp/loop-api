## 一句话结论

**钱包层选 Privy（它是唯一同时把「嵌入式钱包 + 策略引擎 + Agent 签名 + Hyperliquid 官方 recipe」四件事做全的供应商），交易层走「多链现货为主体 + Hyperliquid 作为附加入口」的路线 A′——因为 Apple 3.1.5(iv) 要求永续合约类 App 必须由持牌金融机构提交，perp 做主形态等于放弃 iOS，而 LOOP 是手机 App。**

# 第一章：Hyperliquid 形态冲突分析与路线推荐

## 1.1 先纠正一个前提错误

用户的判断是「Hyperliquid 上币是白名单，没有蜜罐合约」。**这个判断只对三分之一。**

| Hyperliquid 的三类市场 | 上币机制 | 是否有欺诈风险 |
|---|---|---|
| **核心 perp**（app.hyperliquid.xyz 上那几十个币） | 验证者运营、受控上新 | ✅ 基本无合约级欺诈，用户判断成立 |
| **HIP-3 自建 perp DEX** | **完全 permissionless**：质押 500,000 HYPE（当时价值 $20M+）即可部署自己的 perp DEX，前 3 个资产免拍卖，第 4 个起走 31 小时荷兰拍 | ❌ deployer 自选 oracle、自定杠杆上限、自行结算，存在 oracle 操纵与恶意运营风险（靠验证者投票 slash 质押来约束）。**且 HIP-3 市场不在官方前端上线，必须第三方前端接入** |
| **Spot 现货（HIP-1）** | **完全 permissionless**：荷兰拍买 ticker 即可发币，HIP-2 自动做市提供初始流动性 | ❌ 新上币流动性极薄（常 <$500K），价格操纵与 rug 高发 |

已发生的实证：**MON 事件**——项目方花约 $500,000 拍到 $MON ticker，上线后表现「几乎等同于 rug pull」；Hyperliquid 随后单方面把前端显示名改成 MONPRO 以让 Monad 使用 MON 标识，引发「上币≠前端展示」的信任争议。第三方风险评级机构 Hindenrank 给 Hyperliquid Spot Orderbook 的评分是 **C+（41/100，112 个 DEX 协议中排 ~83-87 位）**，首要崩溃场景明确写为「通过薄 HIP-2 流动性操纵 HIP-1 代币」。

**对 LOOP 的直接影响**：如果只做核心 perp，AI 合约安全检测确实失效；但如果碰 Hyperliquid spot 或 HIP-3，风险检测的需求不是消失了，而是**换了维度**（见 1.3）。

来源：[HIP-3 官方文档](https://hyperliquid.gitbook.io/Hyperliquid-docs/hyperliquid-improvement-proposals-hips/hip-3-builder-deployed-perpetuals)、[HIP-3 十问](https://www.bitget.com/amp/news/detail/12560605013899)、[Hindenrank Spot 风险报告](https://hindenrank.com/blog/is-hyperliquid-spot-orderbook-safe)、[MON 事件](https://en.theblockbeats.news/news/60364)

## 1.2 替代关系还是并列关系？——是并列，但有一道硬裂缝

**技术上并列，产品上有一道无法抹平的裂缝：资金账本是割裂的。**

Hyperliquid 的资金不在「用户钱包里」。它在 HyperCore 的 USDC 保证金账户里，唯一入口是 **Arbitrum 原生 USDC 跨桥**（最低入金 5 USDC，出金固定收 1 USDC 手续费，约 3-4 分钟到 Arbitrum）。这意味着：

- Wallet Tab 显示的「多链资产」和 Hyperliquid 的「可用保证金」是**两个不相干的余额**
- 用户想从聊天里点 Buy 直接开仓，必须先完成「某链资产 → Arbitrum USDC → 跨桥入 HyperCore」这条链路，中间至少两次等待
- 「钱包地址 = 社交身份」这个统一身份设计在 Hyperliquid 侧会打折：Hyperliquid 账户虽然也是 EVM 地址，但真正执行交易的是 **agent/API wallet**（一个不能提币、只能下单的授权签名者），而入金/提币/授权 agent/授权 builder fee 这些动作又必须用主钱包签

所以「不离开上下文直达交易」这个核心体验，在现货 swap 上能做到，在 perp 上做不到——除非你预先引导用户把资金常驻在 Hyperliquid 账户里，而那就等于让 LOOP 从钱包变成交易所。

来源：[Hyperliquid Bridge 文档](https://hyperliquid.gitbook.io/hyperliquid-docs/hypercore/bridge)、[Privy Hyperliquid agent recipe](https://docs.privy.io/recipes/hyperliquid/agents-and-subaccounts)

## 1.3 如果 Hyperliquid 成主场，产品会变成什么

**会从「多链钱包 + 社交」变成「perp 交易所前端 + 社交」。这不是同一个产品。**

| Tab | 原方案（多链现货） | Hyperliquid 主场后 |
|---|---|---|
| **Market** | 多链 DEX 行情聚合、新币发现、K 线 | **变简单也变好**：单一数据源（HL WebSocket），有真正的订单簿、深度、资金费率、未平仓量、清算数据。做出来的行情质量比现货 DEX 聚合高一个档次 |
| **Wallet** | 多链资产、转账、Swap、Bridge、DApp Browser | **被架空**：核心变成「一个 USDC 保证金账户 + 仓位列表 + 入金/出金」。多链资产、DApp Browser、Bridge 都成了服务于「把钱搬进 Hyperliquid」的配角。Wallet Tab 实质降级为「资金管理页」 |

**AI 安全层的存废——这是最需要认清的一点。LOOP 现有的 AI 安全层设计里，有一大半是 EVM 现货特有的，perp 路线下直接归零：**

| AI 安全层功能 | perp 场景下 | 说明 |
|---|---|---|
| 合约验证 / 蜜罐检测 | ❌ **归零**（核心 perp）/ ⚠️ 变形（HIP-3、spot） | 核心 perp 无合约可查 |
| 交易模拟 | ❌ **归零** | 下单走签名消息，不是 EVM calldata，没有可模拟的合约调用 |
| **无限授权拦截改写为限额** | ❌ **完全归零** | Hyperliquid 交易不需要 ERC20 `approve`，没有 allowance 这个概念 |
| **授权盘点与一键回收** | ❌ **完全归零** | 同上。这两项是 LOOP 安全层最有差异化的部分，perp 下不存在 |
| 新的可做维度 | ✅ | 资金费率异常、爆仓价距离、杠杆过高预警、OI 集中度（Hyperliquid 头部 0.23% 地址持有 ~70% OI）、oracle 偏离、agent 授权到期盘点（agent 最长 180 天）、builder 授权盘点 |

结论：**perp 路线下 AI 安全层要整体重写**，从「合约风险」转向「市场与仓位风险」。旧设计的复用率约 20%。

## 1.4 三条路线的量级对比

工作量按「一个小团队 + AI 辅助」的相对量级给，不是绝对人日。

### 路线 A：只做多链现货（原方案）

- **要接**：Privy（钱包）+ 0x 或 1inch（EVM swap）+ Jupiter（Solana swap）+ LI.FI 或 Relay（跨链）+ GoPlus/Blockaid（安全）+ 多链余额索引
- **工作量**：**中-高**。难点在广度——每加一条链就要打通「余额索引 + swap 路由 + 安全检测 + 区块浏览器」四件事。跨链桥即使不自研，路由失败、卡单、退款这些运营态问题仍要自己兜
- **月度固定成本量级**（1万 MAU）：Privy $499 + 1inch $199 或 0x（按量）+ GoPlus $199~399 ≈ **$900~1,100/月**
- **收入**：swap affiliate fee，0x 上限 10%、LI.FI 自定义、Jupiter 需分 20% 给 Jupiter。实际可收 0.3%~0.5% 不刺眼
- **合规风险**：**低**。钱包 + 现货 swap 是 App Store 上最成熟的类目，非托管钱包类 App 大量在架
- **最快上线量级**：**季度级**（能上线的 MVP 比 B 慢，但没有生死级卡点）

### 路线 B：只做 Hyperliquid perp（最窄最快）

- **要接**：Privy（钱包 + agent wallet）+ `@nktkas/hyperliquid`（社区 TS SDK）+ Arbitrum USDC 入金
- **工作量**：**低**。这是三条路里技术上最省的：单一数据源、单一资金通道、无跨链桥、无多链索引、无 approval 管理、无蜜罐检测。Privy 有官方 Hyperliquid recipe（quickstart / agent wallet / builder codes / 客户端用法四篇），照抄即可
- **月度固定成本量级**（1万 MAU）：Privy $499 + Hyperliquid API 免费 ≈ **$500/月**。另需 builder 地址常备 ≥100 USDC
- **收入**：builder fee，**perp 上限 0.1%**，无需申请、无审批队列
- **合规风险**：**极高**。见下
- **最快上线量级**：**月级**（技术上），但 **iOS 上架可能永远做不到**

### 路线 C：两者都做

- **工作量**：**A + B，且不止是相加**。多出来的是两套资金账本的对账、两套风险模型、两套行情、两套 UI 语言（swap 滑点 vs 杠杆爆仓价）。安全层要维护两个互不复用的实现
- **月度固定成本量级**：**$1,000~1,200/月**（B 的边际成本很低，主要是人力）
- **合规风险**：**极高，且被 perp 拉高整体**。一个 App 里只要有 perp，整个 App 就落入 Apple 3.1.5(iv)
- **最快上线量级**：**半年级以上**

## 1.5 决定性因素不是收入，是 App Store

先把收入这个常见误判排掉。两条路的收入量级其实接近：

| | 假设 | 月收入量级 |
|---|---|---|
| perp（路线 B） | 1万 MAU，5% 交易 perp = 500 人，杠杆放大后人均月交易量 $50K，抽 0.05% | **~$12K** |
| 现货（路线 A） | 1万 MAU，10% 做 swap = 1,000 人，人均月 swap $2K，抽 0.5% | **~$10K** |

perp 费率低（0.1% 上限）但杠杆放大交易量；现货费率高（可到 0.5%+）但频率低。**收入不构成决策依据。**

而且 perp builder fee 的现实比模型更差。行业已经跑过一遍了：

- Hyperliquid builder 生态累计分成约 **$64.22M**，30 天约 **$5.6M**，80+ 活跃 builder（2026 年 3 月数据）
- 但收入极度集中：**Phantom 一家自 7 月初拿了 $12.6M+**
- **MetaMask 按满额 0.1% 收费，结果被描述为「悄然亏损」——没赚到钱，等于白送了自己的用户流量**
- Hyperliquid 用户结构极度头重：约 110 万钱包、~21.7 万月活、~5 万日活，**头部 0.23%（约 500 个地址）持有约 70% 的未平仓量（~$5.4B）**。钱包集成带来的是低频散户，ROI 低
- 多篇行业分析的共识：对多数钱包来说，接 Hyperliquid 是**低 ROI 的防御性动作**，为了功能齐全和留存，不是为了赚钱

来源：[Hyperliquid builder 生态分析](https://foresightnews.pro/article/detail/95769)、[钱包集成 ROI 分析](https://t-www.panewslab.com/en/articles/73b424a5-4cc6-4b2f-8417-44c152ad9059)、[Builder codes 官方文档](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/builder-codes)

**真正的决定性因素是 Apple。**

Apple App Store 审核指南 **3.1.5(iv)** 明确要求：促成加密货币期货交易的 App **必须来自成熟银行、证券公司、期货佣金商（FCM）或其他获批金融机构**。**3.2.2(viii)** 要求 CFD 及其他衍生品类 App 在**所有提供服务的司法辖区都持有相应牌照**。

LOOP 不是持牌金融机构。这条不是「审核可能比较严」，是**结构性不合格**。

最有说服力的旁证：**Hyperliquid 自己的官方 App，2026 年 4 月 1 日先发的是 Android MVP（Google Play），iOS 至今未发布**，报道明确写「iPhone 和 iOS 用户可能还要等一段时间」。连协议方自己都过不了这道关。

来源：[Apple 审核指南解读](https://mankunlaw.com/index.php/en/article/477)、[Hyperliquid Android MVP](https://www.cryptotimes.io/2026/04/01/hyperliquid-rolls-out-official-android-app-mvp-for-early-testing/)

## 1.6 推荐：路线 A′

**以多链现货钱包为主体上线（路线 A），Hyperliquid 作为 Phase 1.5 的一个附加交易入口接入，但不做成主形态、不进 iOS 主包。**

理由，按权重排序：

1. **iOS 是生死线。** LOOP 是手机 App，六个 Tab 的社交超级应用形态离不开 iOS。perp 做主形态 = 放弃 iOS = 产品死。这一条单独就足以否掉路线 B 和 C。
2. **AI 安全层的差异化在现货侧才成立。** 授权盘点/无限授权改写是 LOOP 目前最有辨识度的功能，它只存在于 EVM 现货世界。perp 路线下这块归零，LOOP 就失去了「AI 安全」这个立身点，退化成又一个 perp 前端。
3. **统一身份闭环需要钱包语义。** 「钱包地址 = 社交身份，一个身份挂多个钱包」这个设计和多链现货钱包是同构的；和「一个 USDC 保证金账户 + agent 签名者」不同构。
4. **收入不是理由，而集成成本极低是理由。** Hyperliquid 接入成本在三条路里最低（Privy 有官方 recipe，社区 TS SDK 成熟），所以「顺手接上作为功能补全」性价比很高——**只要别让它决定产品形态，也别让它污染 iOS 上架资格**。
5. **Market Tab 可以先白吃 Hyperliquid 的行情。** 行情是只读数据，不涉及下单，没有合规问题。Hyperliquid 的 WebSocket 提供订单簿、成交、资金费率、清算，数据质量远好于拼多个现货 DEX。**先接行情、不接下单**，是零风险的纯增益。

### 落地节奏建议

| 阶段 | 内容 | Hyperliquid 参与度 |
|---|---|---|
| **Phase 1** | Privy 钱包 + 多链资产 + 现货 Swap + AI 安全层（授权管理是重点）+ 聊天 Token 卡片直达 Swap | **只接行情**（Market Tab 用 HL WebSocket 拿 perp 行情/资金费率做数据展示），不接下单。iOS 正常上架 |
| **Phase 1.5** | Web 端 + Android 开放 Hyperliquid 下单（Privy agent wallet + builder code），iOS 不开 | 下单能力仅在 Web/Android，或 iOS 内以 WebView 外链形式（需谨慎评估，Apple 对包装外部交易界面同样审查） |
| **Phase 2** | Launchpad / 法币入金 / 挖矿。若届时 perp 收入验证成立且拿到牌照路径，再考虑独立 App 承载 perp | — |

**这个节奏的关键取舍**：接受 iOS 上没有 perp 下单。如果这一点不可接受，那唯一的合规解是「找持牌实体合作提交」或「perp 单独出一个 App 并接受 iOS 缺失」，两者都属于商务/法务问题，不是技术选型能解决的。

# 第二章：嵌入式钱包层对比 + Privy 是否够用

## 2.1 结论先行

**Privy 够用，可以选定。** 它是候选里唯一同时满足以下四条的：

1. 嵌入式钱包非托管 + 支持用户导出私钥
2. 有生产级策略引擎（默认拒绝、合约白名单、单笔限额、链/方法白名单、calldata 约束）
3. 有 Agent Wallet / 服务端程序化签名（intent-based 授权，非裸 API key）
4. **有官方 Hyperliquid 集成 recipe**（quickstart、agent wallet 与子账户、builder codes、客户端用法）

第 4 条是决定性的。它意味着无论走路线 A′ 还是将来加重 Hyperliquid，钱包层都不用换。

**唯一需要提前落实的动作**：签约前书面确认「私钥导出功能不被关闭」，并在 App 内保留导出入口。理由见 2.4 锁定风险。

## 2.4 锁定风险（最严重的一点，重点说清）

**Privy 与 Dynamic、Turnkey、Coinbase CDP 一样，默认钱包是 EOA，签名基础设施由供应商管理。换供应商的现实是：用户拿到新地址，资产要自己搬。**

具体风险分层：

| 层级 | 风险 | 缓解 |
|---|---|---|
| **可缓解** | 私钥导出。Privy 支持导出，但导出是「策略管控的操作」，且行业普遍存在「开发者可在后台关闭导出」的开关 | **签约前书面确认导出不可被单方面关闭，并在 App 内保留常驻导出入口。这是唯一真正的逃生舱，必须落在合同里** |
| **难缓解** | EOA 地址与供应商签名设施绑定。换供应商 → 换地址 → 用户需自行转移全部资产。第三方分析给出的量级参考是 1 万用户的迁出成本约 $5K~$20K，且伴随重新验证、重新引导、空钱包 | 若「长期地址可携带性」是硬需求，架构上应改用**智能合约钱包 + 模块化签名者**（地址不变、签名者可轮换）。Privy 在 EVM 上支持可选 ERC-4337 智能钱包——**如果锁定风险被判定为不可接受，应在 Phase 1 就走智能钱包路线，而不是先 EOA 后迁移** |
| **不可缓解** | **地址 = 社交身份，而 LOOP 的身份系统建在地址上。** 换钱包供应商导致换地址，会连带打断社交图谱、历史记录、声誉 | **这是 LOOP 特有的、比普通 App 严重得多的锁定点。** 建议身份系统不要直接以钱包地址为主键，而是用内部 user id 为主键、地址作为可挂载/可替换的凭证。这样换供应商时社交图谱不断裂。**这个架构决策必须在写第一行身份代码之前定下来** |

另一个被低估的锁定维度：**Privy 已归 Stripe，Dynamic 已归 Fireblocks。** 两家都从独立创业公司变成大厂产品线。好处是不会突然倒闭、支付/合规能力增强；风险是定价策略与产品优先级将服从母公司战略，独立性下降。

### B.3 Builder code 机制（关键商业问题）

**结论：可以抽成，无需申请、无审批队列，门槛极低。**

| 项 | 内容 |
|---|---|
| **perp 抽成上限** | **0.1%（10 bps）** |
| **spot 抽成上限** | **1%（100 bps）** |
| 单位 | API 里以「十分之一基点」表示：`100` = 0.10%（perp 上限），`1000` = 1%（spot 上限）；`50` = 5 bps = 0.05% |
| **builder 门槛** | ① perps 账户价值 **≥ 100 USDC**；② 账户抽象模式为 `standard`；③ 合法 42 字符 0x 地址。**没有外部审批队列** |
| 用户侧授权 | 用户以 **主钱包**（不能用 agent wallet）签 `ApproveBuilderFee`，设定 `maxFeeRate`；每个用户最多 **10 个活跃 builder 授权**；可随时撤销 |
| 每单收费 | 订单带 `{"b": builder地址, "f": 费率}`，`f` 必须 ≤ 用户授权的 maxFeeRate 且 ≤ 硬上限 |
| 查询授权状态 | `{"type": "maxBuilderFee", "user": "0x...", "builder": "0x..."}`，返回 `"0"` 或 undefined 即未授权 |
| 结算 | 走标准 referral reward claim 流程 |
| 覆盖范围 | perp 双边都收；**spot 只收 quote/抵押资产侧，不收买入侧** |
| 最佳实践 | 授权的 `maxFeeRate` 设得比实际收费高，日后调价无需重新授权 |

**同业实际费率**（说明市场行情）：MetaMask 收满 0.1%、Phantom 0.05%、Rabby 0.05%、Based 0.025%、Axiom/Insilico 低至 0.010%。

### B.4 做 Hyperliquid 前端的先例说明什么

两种集成路径已被跑通：

| 路径 | 采用者 | 工作量与代价 |
|---|---|---|
| **直调官方 API** | MetaMask、Rabby、Axiom | **快**，但受 rate limit 与官方更新影响，控制力弱 |
| **自建只读节点 + 后端中继** | Phantom | UX 与稳定性更好，但**存储成本高、数据一致性风险、技术复杂度大** |

**对 LOOP 的结论：直调 API 路径的工作量是「周级」，这就是为什么建议顺手接上。** 但要清楚这条路的天花板——受限流约束、无差异化。真正的差异化（自建节点）成本高到不适合小团队。

同时必须记住 1.5 节的 ROI 数据：**MetaMask 走的是最省的直调路径、收满 0.1%，结果仍是「悄然亏损」。** 且 Hyperliquid 官方 App 上线后会进一步压缩第三方钱包的空间。

# 第六章：遗留待确认问题

按优先级排序。前三项建议在写代码前解决。

## 🔴 必须先解决（阻塞架构决策）

1. **身份系统主键用什么？**
   若以钱包地址为主键，换钱包供应商 = 换地址 = 社交图谱断裂（第 2.4 节）。建议用内部 user id 为主键、地址作为可挂载凭证。**这个决策必须在写第一行身份代码前定下**，事后改造成本极高。

2. **EOA 还是智能合约钱包？**
   EOA（Privy 默认）便宜简单，但地址与供应商绑定，迁移必换地址。ERC-4337 智能钱包地址不变、签名者可轮换，可携带性强得多，但 gas 更贵、Solana 侧不适用。**若判定锁定风险不可接受，应在 Phase 1 就走智能钱包，而非先 EOA 后迁移。**

3. **iOS 上没有 perp 下单，是否可接受？**
   这是路线 A′ 的核心取舍。若不可接受，需走商务/法务路径（找持牌实体合作提交），技术选型无法解决。**这是产品决策，不是技术决策，需要用户拍板。**

5. **Privy 私钥导出能否被单方面关闭？**要求写进合同。这是唯一逃生舱，也是抗辩「非托管」的技术依据。
